# Markdown reader and editor

The Markdown slice retains exact agent responses, file snapshots and deliberately published documents in a private local store. Publication saves silently; the operator chooses when to open a document in the native Mac app. An agent puts a document in front of the operator by running the publication's `show` command as the program of a terminal pane without a target and without taking focus. An ordinary session opens it beside its own pane: as a split on the right, or as a floating pane over its window when `markdown.agentPane` is `float`. An agent without a pane of its own, such as a worker, always opens a floating pane on the tab of the ordinary session that started its chain of agents ([Rex inherited context](../rex/README.md#select-the-right-work)). The native reader window then sits over that pane. Ordinary Pi and native Durable tools share the same publication operation and structured result.

The native Mac pane shows one web page with two states: Reading and Writing. The Edit button or ⌘E changes the state without opening another interface. Reading clicks select text or follow links; they never edit. In Writing, a click opens that block's Markdown on the same page. Edits save automatically. Captured responses and file snapshots never change: Writing creates a copy on the first change. Passage comments send quoted context and a request to the exact Pi conversation that opened the pane. `markdown_live` reads and changes that active buffer without a save/show exchange. Recovery snapshots stay private and do not appear in stored-document reads. See [recovery, saving and reading state](native/README.md#recovery-saving-and-reading-state) for source fidelity and recovery boundaries.

Plain document opens, including published documents, captured responses and file snapshots, start in Reading. New drafts, explicit Edit and Copy opens and explicitly edited files start in Writing. Retained drafts restore their remembered state, initially Writing; an explicit edit open takes precedence. The pane retains Reading or Writing choices only for drafts, separately from document reading positions.

A right-click or Control-click shows the reader's own menu, never the system menu. It lists the actions for the place clicked, with their shortcuts: Ask about this, the clipboard actions, Copy with Source, the formats in Writing, the actions of a link, image, code block or table, Edit Here or Edit Selection, Find and the Reading or Writing switch. Cut, Copy and Paste show as unavailable when they cannot run; other actions that do not apply are left out, and where no action applies, no menu opens. Arrow keys, Return and Escape work the menu, and it keeps the caret, the selection and the scroll position. Its clipboard actions use the host's pasteboard, so Paste shows no permission prompt.

## Store format

The store uses format version 1. Directories have mode `0700`; files have mode `0600`. The TypeScript store owns all document writes. Readers take no lock. `identity()` reads the store identity without creating a directory or taking the writer lock; an absent store returns no identity, and invalid metadata is a store error. The native application keeps reading state and recovery outside this store. Reading removes accepted open requests but never changes document source; editing uses the bundled writer.

```text
store.json                                  {version:1, storeId:<32 hex>}
documents/<id>/document.json                 published document pointer
snapshots/<id>/document.json                 response or file snapshot pointer
documents/<id>/revisions/<n>/source.md        exact UTF-8 source
documents/<id>/revisions/<n>/revision.json    immutable revision metadata
documents/<id>/revisions/<n>/assets/<digest>.<ext>
sources/<sha256(sourceKey)>.json             snapshot source index
reuse/<sha256(reuseKey)>.json                explicit-reuse publication plan
opens/<uuid>.json                           transient pinned open request
```

Document IDs contain `md-` and 20 random lowercase hexadecimal digits. Titles, paths, host identities and app locations are not document identities. A complete document directory is portable to the same-named collection of another store with its identity, revisions and retained assets intact. Published documents live in `documents/`; response and file snapshots live in `snapshots/`. Both collections use the same revision layout. The source and reuse indexes are local to their store. The installed app is a separate program at `markdown.app`, never part of a document store.

`document.json` contains `version`, `id`, `kind` (`published`, `response` or `file`), `title`, `createdAt`, `updatedAt`, `revision`, `digest` (`sha256:<hex>`) and `bytes`. The pointer is replaced by rename only after a complete revision directory exists. Readers validate every pointer field before they filter, sort or return a document: titles follow the writer's bounds, timestamps use canonical UTC ISO form, digests use the source digest format, and byte counts are safe integers within the source bound. Listing counts an invalid pointer as unreadable without discarding healthy documents. Readers ignore revision directories above the pointer.

`revision.json` contains `version`, `document`, `revision`, `title`, `createdAt`, `digest`, `bytes`, `completeness`, `contentOrigin` and `references`. Published revisions also contain a random `publication` identity. `completeness` has `state` (`complete` or `partial`) and optional `reason` and `note`. `contentOrigin` records the source kind, capture time and available host/session/conversation/entry/model/path/working-directory/part-length provenance. Provenance does not control execution or identity.

`references` contains `state` (`inspected` or `uninspected`), `truncated`, `omitted` and `items`. Each item contains `kind` (`image` or `link`), the original `reference`, and `state` (`retained`, `embedded`, `external`, `unavailable` or `local-only`). Retained images include `file`, `mediaType`, `bytes` and `digest`; unavailable images include a fixed `reason`. Metadata keeps at most the first 512 characters of a reference, and an embedded data reference keeps only its first 64; the exact source keeps every whole destination. A retained image keeps its whole reference, because the reader finds a stored image's item by its whole reference. An image whose item holds a shortened reference therefore reads as unavailable. A shortened image reference that equals another image destination is not listed, so it never names that image's item.

An uninspected inventory of a publication or file snapshot whose inspection did not run carries `reason`: `app-missing` (no installed reader app), `app-incompatible` (another contract, or no headless tool), `tool-failed`, `tool-timeout` or `output-invalid`. Response snapshots are uninspected without a reason, because response capture does not inspect references.

Only inspected revisions contain `selfContained`. It is true only when every listed reference is retained or embedded, `omitted` is zero, and `truncated` is false. `omitted` is the exact count of known items that the metadata does not list: items beyond the item bound and shortened image references left out as described above. `truncated` separately indicates that the parser stopped at its destination bound, so further coverage is unknown. Uninspected records contain no reference items and make no self-containment claim. Response snapshots are uninspected.

A response source key names host kind, conversation/session and entry identity. A file source key names its real path. Equal source key and equal captured content return the existing snapshot. Captured content is the source digest, the reference coverage (`state`, `truncated`, `omitted`) and each listed reference with its state, reason and retained asset identity (file, media type, bytes and digest); capture time, provenance and the cause of a failed inspection are not content. Changed captured content adds a revision to that snapshot: a replaced or missing image, or an inspection that became available, adds a revision even when the Markdown is unchanged. The source digest remains the digest of the exact Markdown bytes, and each earlier revision keeps its own retained assets. A snapshot directory can be removed by hand. The source index is a local hint: a dangling entry recreates the snapshot under its reserved ID. The index is published before the snapshot, so process termination between those writes does not create a duplicate. Explicit publication updates require the exact current revision; stale updates return a conflict with the current revision and digest.

All store mutations share one cross-process `proper-lockfile` lock at `<root>/.lock`. A writer reads and validates source and assets before it takes the lock. It writes new documents and revisions in private temporary directories and publishes them by rename. A writer adopts an unpublished orphan only when its publication identity matches its own plan; otherwise it replaces the orphan. A crashed, unpublished update conflicts if another writer published first. No acknowledged revision is replaced. A write that fails removes its own staging directory. Under the lock, each document write also removes `.tmp-*` staging directories older than one day from the first 2000 entries of both collections and from the revisions of the document it updates; committed documents and revisions never have that name. The writer refuses a revision whose `revision.json` would exceed 256 KiB, the reader's limit for a store record, with `too-large`. Atomicity covers process termination, not power loss: the store does not synchronise directory entries or perform a full device flush.

A publication plan contains `publicationId`, `documentId`, `revision` and `inputDigest`. The input digest identifies canonical invocation arguments, not later file or asset bytes. For native explicit reuse, the writer first selects or installs the reuse index plan. The tool then memoises that exact plan before any document write. A crash before the memo leaves only an index plan that the recovered task selects again. A replay returns the original published revision even after a later update. An explicit `reuseKey` persists the plan before the document write; equal arguments return or complete it, and different arguments return `replay-conflict`. Index records become visible complete, under the writer lock. Temporary index files are not records.

An open request contains `{version:1, storeId, document, revision, digest, requestedAt, launchOrigin}`. It pins one existing revision. Terminal return context belongs only to this request and the resulting window, never document metadata. The reader verifies the store identity and digest, then removes an accepted request. The writer prunes leftover requests older than one day, within a bounded scan.

## Native editor writer

The [native editor writer contract](editor-writer.md) exposes a short-lived JSON helper over the same TypeScript store. It accepts exact store and base identities, retains checked images, distinguishes editor authorship and copy derivation, and reconciles lost save responses through the existing replay index. Blank editor source is valid. Draft recovery and local-file writes are separate from committed document revisions. The publication tool's capture and nonempty-source rules do not change.

## Publication tool

`markdown_publish` requires `title` and exactly one of `text` or `file`, or `response: "previous"` alone. A file path is explicit, absolute or relative to the working directory; the operation never modifies that file. Images that a file links by relative path are retained with the revision, so an agent explains something visually by writing an SVG or PNG diagram beside a Markdown file and publishing the file. Updates supply `document` and `expectedRevision` together. A text publication reads no image files. In a text update, an image reference that the revision named by `expectedRevision` retained keeps that revision's retained bytes, after their digest and size check; reference coverage then carries `kept` (that revision and the number of images), and the text result says that a file publication changes an image. Other local image references of a text publication stay unavailable with reason `no-base`. Optional `reuseKey` requests explicit reuse. Separate identical creates without a key remain separate documents.

`response: "previous"` saves an earlier answer exactly instead of new text: the newest assistant response with text before the newest user message, on the current branch of an ordinary session or in the calling native conversation. It uses the same response snapshot, source key and title as the operator's own capture, so the same response always names the same snapshot document, and a repeated call returns it again. It takes no title, document, expected revision or reuse key. A new explanation of that answer, such as a diagram, is a separate publication with its own title; it never replaces the snapshot.

Both hosts return the same structured outcome. Success includes `ok:true`, document ID, revision, source digest, byte count, title, kind (`published` or `response`), created/replayed flags, reference coverage, provenance, `open` (the `/markdown <id>` command of an ordinary Pi session), either `show` (the [pane reader](#reader-in-a-terminal-pane) command for the document) or `showUnavailable` (why no command is offered, with the build command), `panes` (the number of reader panes connected to the publishing conversation, present when `show` carries the live connection through which a pane reports itself; a pane leaves the count when it closes), and `selfContained` only after reference inspection. Reference coverage (`references`) has the inventory `state`, `truncated`, `omitted`, the counts `retained`, `embedded`, `external`, `unavailable` and `localLinks`, `reason` when inspection did not run, and `unavailableItems`, the first five unavailable images with their reasons and references shortened to 120 characters; the revision record keeps the complete inventory. The text result adds one line of capture qualifications when the inventory is partial, an image is unavailable or inspection did not run, with the cause and its remedy. `replayed` is true only when a saved publication is returned again; a newly completed write, including the first keyed publication, reports false. Failure includes `ok:false` and a bounded error with code `invalid`, `too-large`, `not-found`, `conflict`, `replay-conflict`, `file-unreadable` or `store-failure`. Conflicts include the current revision and digest.

Tool cards use the same presentation conventions as other harness tools: the tool name, a concise subject and outcome, and expanded arguments or evidence through the host's configured key. Normal cards do not repeat navigation instructions or expose document bodies. The text result for the agent names the saved identity, revision, byte count and digest, and says whether the call saved a new document, saved an update, or returned an earlier publication again; a replay says that later changes to its text, file or images are not in it. It adds one line of capture qualifications when they apply, then the next action: the `show` command as a JSON array to run as the program of a new pane, a note that a reader pane that still shows an updated document follows the new revision by itself, or the reason that no command is available. For an update with a known `panes` count of zero, the note says instead that no reader pane is connected to the conversation, because the operator may have closed it, and that no pane of the agent shows the revision; with no connected pane, the note offers no `:open` input either. A conflict adds the recovery: read the current revision with `markdown_read`, apply the change to that text, and publish again with that revision as `expectedRevision`. Stable guidance lives in the tool description, which asks for one pane per document, opened only when the operator should read it now, without a target, so that it opens on the tab where the work belongs, that closes when its program ends, without taking focus. In an ordinary session the description and its prompt rule name the pane that `markdown.agentPane` selects: a split on the right of the session's own pane, or a floating pane that stays in place. Native tools and the native guidance section always name a floating pane that stays in place, because a native agent has no pane of its own. The guidance names the pane only, not a default or the setting behind it, so an operator's request for another pane governs without further rules. Connected buffers use `markdown_live` for corrections; stored-publication updates retain their explicit revision contract. The description adds that the operator can close a reader pane at any time, so an agent tells the operator that a pane shows an update only when the result shows a connected pane; otherwise it shows the update in a new pane or says that it is saved. The description also asks that a different document appear in a reader pane that the agent opened earlier, by typing the outcome's `paneInput` into that pane, instead of adding another pane, and that an agent type into or close only reader panes that it opened itself. Ordinary tools return `structuredContent` and presentation details. Native tools return `structuredOutput` and presentation details. Native publication declares `replay: "safe"` and memoises its random publication plan in the Durable tool task before the document write. A recovered task returns a saved receipt before it reads the original file again. A native response snapshot needs no memo: its source key makes a repeated write return the same snapshot. Publication performs no reveal, app launch or focus action.

## Read tool

`markdown_read` finds and reads stored documents exactly in both hosts, with the same structured outcome. It opens no window, starts no model work, takes no writer lock and changes no document data. A returned `show` command can create a private one-use connection file.

- Without `document`, it lists the newest documents of one collection (`kind`: `published`, the default, `response` or `file`), optionally those whose title or ID contains `query` (literal, case-insensitive). The outcome has at most 20 rows, `matched` (all matching rows among the scanned entries), `scanned`, `unreadable` (document directories whose pointer is missing, unreadable or invalid) and `bounded`. A bounded scan lists the newest scanned documents, not the newest stored ones. `contains` (literal, case-insensitive) searches the revision named by each candidate in the listing, newest first, at most 200 documents and 32 MiB of source per call; a concurrent update does not change that candidate's searched source, identity or byte accounting. Matching rows carry the first matching line (`excerpt`, its 1-based line number and at most 160 characters). The outcome's `search` states `candidates`, `searched`, `bytes`, `complete` (every candidate was searched) and `unreadable` (sources that failed their checks). Title matching and source search are separate filters; both apply when both are given.
- With `document` (an ID or a unique prefix of at least six characters), it reads the exact source of the current revision, or of `revision`, in pages of at most 64 KiB of UTF-8. `offset` and `nextOffset` count UTF-16 code units and never split a surrogate pair; a continued page requires the revision of its first page. A page names the document, kind, current title and current revision, the read revision with its title, creation time, digest and byte count, completeness, `selfContained` when inspected, reference coverage as in publication outcomes, and provenance. The first page also lists up to 32 images with their state, reason, media type, bytes and digest, references shortened to 160 characters, and `imagesOmitted`, and carries the same `show`, `paneInput` or `showUnavailable` as a publication outcome, so an agent that found a document can show it without knowing the store root or app path.

The text result has two parts: a header with identity, revision, digest, capture qualifications and the continuation arguments; then the exact page of source. A current published revision's header supplies the `expectedRevision` that an update needs. A historical revision's header instead requires a read of the current revision before a correction, so an agent applies the correction to current text rather than historical text. Native read output declares byte and line limits that retain a complete source page and its header, including a page filled with newlines. Ordinary Pi passes the extension's text parts through without a default text limit. Provenance is data about capture; it does not authorise execution or name a current recipient.

## Live collaboration

Select a passage in Reading or Writing and choose **Ask** in the selection strip, or **Ask about this** at the top of the right-click or Control-click menu. A card floats beside the passage inside the pane at every width, below it or above it when space below runs out, and never covers the selected text; it shows the quote and a message field, which takes the keyboard. Opening the card never scrolls the page. Command-Return sends; Return adds a line, and composition input never sends early. Escape or the close control dismisses the card. Command-Shift-M asks about the selection; Command-Option-M and the Ask button address the whole document. The card shows progress, then the agent’s reply beneath the question. Paragraph breaks stay intact. The conversation keeps its copy. If a reply exceeds the pane’s text limit, the card shows the beginning and tells you where to read the rest. Agent changes show a passage highlight and a notice with Show and Undo. No agent change takes focus or scrolls the page.

**Show changes** compares the old and new wording in separate Before and After rows. Only the words that differ are marked; an insertion or deletion has one labelled row. For a long edit that exceeds the word-comparison budget, both versions appear without highlights. If a later edit overlaps the change, the panel identifies the comparison as the original agent edit, not the current document. Previous and Next appear only when there are other changes to review. For a question, they include edits from follow-ups in that thread. **Back to question** reopens the associated conversation and focuses its message field; an edit without a known thread has no such link. Undo reverses the selected agent operation, not every change in the thread. Escape closes the comparison.

**Ask about the selection** stays disabled in the Ask menu until you select text. The quoted passage is context, not an edit range or instruction. The agent uses `markdown_live` to read context and edit the current buffer. Comments use the existing route to the invoking conversation. Unsent comments remain in memory for their exact document. The comment field stays enabled during send. A retry keeps the original request ID, text and quote; a successful receipt never clears newer typing. A definite rejection preserves and unlocks the draft. Durable admission failures retry the same idempotent request. An ordinary route with unknown admission does not resubmit and asks the person to check the conversation. Ordinary Pi reports a request, not durable admission. The bridge waits for Pi to start the exact submitted user message before it follows the reply through tool calls. If Pi takes multiple user messages together, each affected question gets a notice instead of an answer from the wrong conversation turn. Durable uses the admitted submission’s own answer. Each pane receives updates for its own requests; asking another question does not discard a previous answer. After an update, reload Pi and reopen its reader panes to use the new route. The page holds the active buffer and its Undo history; the native mirror checks each change and retains recovery while both the person and agent edit.

`markdown_live` supplies:

- `op: "apply"`, `handle`, `edits: [{find, replace}]`: replace exact text in the unsaved buffer. Each `find` must occur once, and matches must not overlap. All matches use the same snapshot. On LF buffers, the tool converts CRLF and lone CR in both fields to LF. It suggests real line breaks or tabs when a literal `\n` or `\t` prevented a unique match. It never applies the suggestion on its own.
- Anchored apply reads the current buffer for you. Omit `baseGeneration` and `baseDigest`, or supply both. If the base changes, the tool resolves the anchors once more and reports `retried: true` if it sends an edit with the refreshed base. If it cannot apply, `stale` includes the current version when the pane supplies one.
- For a claimed passage, `apply` also accepts `edits: [{start, end, expected, replacement}]` with the exact read base. Use ordered, non-overlapping UTF-16 ranges and do not mix edit forms. The pane's Undo owns the transaction. `applied` confirms private recovery retention.
- `op: "list"`: active handles in this exact conversation.
- `op: "read"`, `handle`: exact source pages of at most 64 KiB UTF-8, whole-buffer `generation` and `digest`, asset identities, `offset`, `nextOffset`, `totalChars` and `totalBytes`. Offsets and character totals use UTF-16 units. Continue with the returned `nextOffset` and the same `baseGeneration`/`baseDigest`; a changed buffer returns `stale`.
- `op: "claim"`, `handle`, `baseGeneration`, `baseDigest`, `ranges`, optional `label`: claim the passages before composing a larger edit. Ranges are ordered, non-overlapping UTF-16 `start`/`end` pairs; labels contain at most 80 characters on one line. Success returns `claimed`, `claimId` and `expiresAt` in milliseconds since the epoch. The passage shows where the agent works. A claim never blocks the person and expires after 90 seconds.
- `op: "release"`, `handle`, `claimId`: end a claim; success returns `released` and the same `claimId`. A successful apply also ends all claims for that handle. Claim and release require `live: 2` on the handle returned by list.

While the person has a block open for writing, from the click that opens it until they leave it, that passage is held, including during an input-method composition. An overlapping claim or apply returns `busy` with a message that names the held range; the pane shows the person "The agent wants to change this passage." with Let it. Read again after the person leaves the passage, or edit elsewhere. Claims do not override this hold. A changed base returns `stale` instead. Sending a request from the pane's ask card closes the person's open block first, so the request itself is never held back. Let it closes the block; when the held request has already ended, the pane asks the agent in the same thread to make the change now.

Undo follows attention: with a block open, Command-Z undoes the person's typing in that block, even after an agent changes another passage. With no block open, Undo reverses the latest change by anyone. An agent change also has its own Undo on its notice and ask card. This Undo reverses that change after later edits unless a later edit overlaps it; a refusal changes nothing. Redo restores the reversed change.

`operationId` is optional. Retry an unconfirmed operation only with the returned UUID and all other arguments unchanged. A remaining `stale` result requires a fresh read and revised edit. If the handle is closed, reopen the same document and list handles again before editing. Selecting another open document suspends the previous handle without retiring it; selecting it again reconnects the same buffer and retains its prompt receipts. Closing a document permanently retires its handle, even when it is not selected. A closed handle never selects another document. A timed-out read releases its queue slot and permits a fresh read; an uncertain edit retains its operation identity for reconciliation. Reads and edits address the live buffer rather than a stored revision.

The connection is a transient Markdown-owned loopback service, scoped to one host lifetime and conversation. A `--live` argument names a private, one-use configuration file, not a token in command output. The native app checks its owner, permissions and identity before consuming it. An unused launch file lasts only until its bridge closes: a session switch, fork, tree change or host shutdown closes the relevant route and removes its unused files. Normal process exit also removes files created by that process. Cleanup uses only exact paths that this process created; it does not scan the directory or infer ownership from file age. Files left by an unexpected process termination have no recorded process owner and remain untouched. Authenticated JSON requests reject browser origins and redirects. The native transport retains whole buffers up to the source limit; model-facing reads page them without truncation.

Ordinary pane opens, attached owner views and tool-returned `show` commands attach this connection when the app declares `live: 1` or `live: 2`. The native connection advertises its version on `/connect`; list exposes it on each handle. Only version 2 offers claim and release. Reusing a consumed or expired launch file leaves saved content readable with an agent-connection-unavailable notice and collaboration disconnected; it never searches for another conversation. Read the stored document again with `markdown_read` to obtain a fresh `show` command for the current conversation. Publication remains separate from live editing and opens no window by itself.

## Reader in a terminal pane

The receipt's `show` array runs the installed reader app in pane mode:

```text
<markdown.app>/Contents/MacOS/MarkdownReader --pane --store <store root> <document ID> --live <private one-use file>
```

The publishing host builds it from its own `markdown.app` and store root, so it runs on the same machine as the store. It is offered only when that app's `build.json` declares contract 1 and pane mode 1 (`pane-command.ts`); otherwise `showUnavailable` names the reason and `node extensions/markdown/native/build.mts`. When the build also declares `paneOpen` 1, the outcome carries `paneInput`, `:open <document ID>` followed by a carriage return: typed into a reader pane that runs already, it shows this document in that pane instead of a new one. `paneOpen` is separate from the pane mode, so Pi processes that started before the app gained this input still offer the pane command. The command names no terminal application: any split or floating pane of a terminal that exposes its screen as a macOS accessibility text area with a visible character range, and whose programs have accessibility access, can host the reader.

The program is the pane's process. It puts the real reader window, with WebKit text, selection, copying, find, links, outline, text size and revisions, exactly over the pane's terminal area as a separate window, keeps it there while the pane moves or resizes, hides it while the pane is not on screen, and closes it when the pane closes. Content of the terminal window that lies over the pane, such as a floating pane, stays visible through a transparent hole in the reader window that passes clicks to the terminal; when such content covers the whole pane, alone or together, the reader window hides. A terminal integration that offers the [pane stacking contract](../../docs/conventions/pane-stacking.md) decides which content lies above the pane, and the reader cuts holes only where it finds that content drawn on screen; without the contract the terminal's accessibility hit test decides, and two overlapping floating panes can be shown in the wrong order. The pane follows new revisions of its document at the reading position of the moment of replacement, waits while the reader scrolls, selects text or has the find bar open, and keeps a revision that the reader picked. `q` in the pane or Command-W in the reader ends the program with status zero, so a pane that closes on success closes with it; if the reading position was not saved, or its save was not confirmed, within about a second, the program ends with status 1 and a line that says which. A wrong store, a missing document or a missing terminal ends it with an error line and a nonzero status before the terminal changes. Without accessibility access the pane says so and shows no window. The [native pane mode](native/README.md#pane-mode) defines placement, focus, keys, revision following and shared reading positions.

A reader pane shows another document of its store when `:open`, a full document ID and Enter are typed into the pane, for example through the terminal's input delivery to a pane that the agent created: the reader saves the shown document's reading position, then opens the other document at its saved position, and the pane keeps its place, size and owner. A document that cannot be read leaves the shown one in place, and the placeholder says why. The placeholder names the shown document ID, its revision, a newer revision when one is available, and the reader build, so an inspection of the pane's screen tells which document and build it runs. The pane itself belongs to whoever created it: input to a pane or its closure needs that ownership, and Markdown neither finds nor closes panes.

Opening a document again starts a new reader at the saved reading position; the document never depends on the process that showed it.

## References and limits

The approved cmark parser is the only Markdown parser. The app's headless `Contents/MacOS/markdown-core references` command receives exact source on stdin. The TypeScript side checks `Contents/Resources/build.json` contract 1 first, limits execution to ten seconds, stdout to 4 MiB and stderr to 4096 bytes. Its versioned inventory has image and link destinations in document order, no duplicates, and at most 4096 destinations per list. A missing, incompatible or failed tool leaves the saved document uninspected and records the cause as the inventory's `reason`. Build the tool with `node extensions/markdown/native/build.mts`.

HTTP, HTTPS and protocol-relative images are external. Data images are embedded. Other schemes are unavailable. Local images require a file source, a regular file with a real path inside the source directory, an allowed media type and bounded bytes. The containment check binds the opened descriptor's device and inode to the contained canonical path identities before and after the read. Absolute paths, traversal and symlink escapes are unavailable. Relative or `file:` links are local-only. Web, mail and in-document links require no local asset. Inspection and capture do not fetch network resources.

Limits: source 2 MiB UTF-8; title 200 Unicode code points on one line (joined emoji and combining marks are allowed); retained images 64 per revision, 8 MiB each and 32 MiB total; metadata 256 reference items and 256 KiB per revision record; listing 2000 documents. Allowed image types are PNG, JPEG, GIF, WebP and SVG. Over-limit source is refused, never truncated. Over-limit assets remain unavailable with a reason. `list()` defaults to published documents. Listing scans at most 2000 entries in the selected collection, filters and sorts by newest update, then applies the result limit. Prefix lookup reads names only in both collections, with a separate limit of 100000 names per collection. Listing and prefix lookup report coverage bounds instead of claiming a complete result; listing also counts unreadable document directories instead of omitting them silently. An absent collection lists as empty; a collection that cannot be opened is a store failure. Retained documents do not expire as caches.

## Ordinary Pi

- `/markdown` or `ctrl+alt+r` reads the latest retained assistant response with text on the current branch, in a native reader split beside this conversation in the same Rex tab.
- `/markdown new` opens a blank private scratchpad beside this conversation. It creates no published document and starts no model work.
- `/markdown edit <id or unique prefix>` edits a published document. `/markdown copy <id or unique prefix>` edits a separate copy of a stored source, including a captured response.
- `/markdown edit file <path>` explicitly edits a local UTF-8 Markdown file. Edits save automatically with file identity checks; the read-only `file` form below still captures a snapshot.
- `/markdown recent` lists recent responses, newest first, with age and size (KB from 1024 bytes). A short acknowledgement does not hide the preceding response.
- `/markdown published` lists deliberately published documents, newest change first, with the short ID, revision and age.
- `/markdown <id or unique prefix>` opens a stored document. Prefixes require at least six characters.
- `/markdown file <path>` captures an explicit local file encoded as UTF-8 and opens its snapshot. Paths resolve against the session working directory; a leading `~` names the home directory. Double quotes around the whole path are optional.
- `/markdown window` deliberately reads the latest response in a separate Mac window, including outside Rex. `/markdown window file <path>` and `/markdown window <id or unique prefix>` use the same selection rules. `window new`, `window edit <id>`, `window edit file <path>` and `window copy <id>` explicitly choose a separate editor window. No pane failure selects this form automatically.
- `/markdown update` builds and installs the reader app from this harness now, in the background, whatever app is installed. See [Keeping the reader app current](#keeping-the-reader-app-current).
- `/markdown help` describes every form. `/markdown help new`, `recent`, `published`, `edit`, `copy`, `file`, `id`, `window` or `update` shows that form's usage and individual notes.
- Any other argument answers with the complete command usage.

`/markdown recent` and `/markdown published` open the Markdown view below the transcript, following the [operator panel convention](../../docs/conventions/operator-panels.md). Browsing does not create a reader pane. Enter or the Read control opens the selected item beside this conversation; `l` reads the latest response, `n` selects Recent responses, and `p` selects Published. `/` filters the list. `w` starts New, `e` edits the selected published document or opens a response with Edit a Copy, and `c` opens a published document as a separate copy. The key row and More menu use the same actions as the keys. Tab moves among regions, and PageUp and PageDown read the detail. Read stays the default action. Selection and preview never reveal an app.

Stored snapshots remain openable by ID after the producer exits; the reader app owns snapshot browsing through its library and recents. Argument completion uses Pi's description field for each option. File and ID forms show usage without inserting a fabricated path or document ID; help topics complete individually. The shortcut appears in Pi's shortcut inventory. Print, JSON and RPC read calls save but never launch the GUI. Editor actions require the local interactive surface and refuse in those headless modes. The outcome uses the host's notification channel when the host has one. The command writes no session message or stdout output.

## Composer

Use `/compose` in an ordinary interactive Pi session in Rex on macOS. It opens a native editor below Pi, or focuses the existing composer. The installed Markdown Reader app must declare `composer: 1`, `contract: 1` and `pane: 1` in `Contents/Resources/build.json`. Set `markdown.composer` to `auto` to open at startup in eligible sessions. The default is manual.

The terminal keeps the transcript. While the composer is present and visible, Pi hides its editor and working row, and the harness statusline hides its footer through the [composer presence contract](../../docs/conventions/composer-presence.md). Type or paste in the focused Pi terminal to insert text in the composer. Press Enter in the terminal to focus the composer. If the composer hides or goes more than three seconds between event polls, Pi's editor becomes usable again with the latest draft Pi received. The connection stays open across a poll gap. Once the composer is present and visible again, Pi hands back any terminal edit, including an empty draft. Pi does not forward its own clear after a submission while the composer is present and visible.

Send uses Pi's Enter handler; Follow-up uses Pi's Alt+Enter action. Stop uses Pi's interrupt action. Completion uses Pi's installed autocomplete provider. Model and thinking choices use Pi's session controls. The composer receives the current branch's recorded assistant cost in USD. The queue display tracks composer submissions made while Pi is busy, not a complete inventory of Pi's queue. Edit queued restores all queues through Pi's own action; its reported count covers only composer-tracked rows. History recalls up to 100 entries and 256 KiB of text from the current branch and input in this composer session.

`/compose close` returns the mirrored draft to Pi's editor. Reload, new, resume and fork attempt to reconnect the same composer and preserve terminal edits made during the handoff. Pi closes the connection and restores its editor if the composer fails to attach in ten seconds or its process exits. Pi mirrors drafts up to 1 MiB of UTF-8; the native app owns recovery for text not delivered to Pi. A pane creation result whose effect is uncertain never triggers an automatic retry.

## Keeping the reader app current

The reader app is a separately built program, so a harness update leaves it as it was. In an interactive Pi session on macOS, each start and each `/reload` compares the installed app's `build.json` with the reader sources that this harness loaded. The check does not delay startup.

- An app built from these sources stays as it is.
- A missing or unreadable app, an app whose build records no source commit, and an app built from an earlier commit of this checkout are replaced without asking: Pi runs `native/build.mts` as a separate process. The footer shows the update while it runs. Notices name its process and log, then report the outcome and how many open readers still run the previous build.
- An app built from a later commit, or from local changes at this same commit, stays installed without a notice: it is a newer build than this harness.
- When the order is unknown, the app stays installed and a notice names `/markdown update`. That covers a recorded commit that this checkout does not contain, a harness with uncommitted reader changes, and a harness outside Git.

Order comes from Git ancestry between the commit that `build.json` records and the commit of the loaded checkout. `/markdown update` installs from this harness whatever the installed app is, unless an install is already running. Only interactive terminal sessions check; print, JSON and RPC modes never check or build on their own. An update outlives the session that started it; only that session's notices and footer status stop. Running readers are never stopped: each keeps its build until it is closed.

The update keeps its files beside the app: `update.log` holds the output of the latest automatic or `/markdown update` run, and `update-failure.json` records the source digest of a failed run. Startup does not retry that digest; `/markdown update` does, and a successful install removes the record. The build itself holds `install.lock` and compiles in `build-cache` there (see [Build and checks](native/README.md#build-and-checks)). A trial that must leave the live app alone sets `PI_MARKDOWN_APP` to its own path; its check, build, cache and records then stay beside that path.

## Attached Agent terminal

Open **Owner views** with `o`, then select **Markdown**: click its tab, or press Tab until the row of owner views has the focus, choose with Left or Right and press Enter. The same owner view is available from the `/agent` dashboard. It binds to the selected conversation and supplies Read latest, Recent responses and Published documents. Enter reads the selected item; `l`, `n` and `p` match the footer actions. New, Edit and Edit a Copy use the same explicit local actions and keys as ordinary Pi. They do not submit conversation text. The attached terminal does not interpret an ordinary `/markdown` slash command: use the owner view instead of sending that text to a conversation.

The native contribution advertises `operator-panel.ts` and the `markdown` owner command under the [attached panel convention](../../docs/conventions/operator-panels.md#attached-panels). Its finite request union is:

```ts
{ op: "recent" }
{ op: "response", entryId: string, offset: number }
{ op: "published" }
{ op: "live" }
```

With no structured data, the command returns bounded text previews and published IDs. Structured calls validate the operation and fields; malformed requests fail. `recent` returns response rows with message timestamps, a captured cutoff, visited-entry count and stop reason. `response` returns at most 256 KiB of text with entry identity, UTF-16 offset/continuation, total characters and bytes, SHA-256 digest, source-part lengths, response timestamp, completeness and provenance. Offsets must be code-point boundaries. The client validates every page and the complete reassembled digest before saving. `published` returns bounded rows, the host's store root, whether the scan stopped early (`limited`) and the count of unreadable document directories (`unreadable`). A present store supplies its store ID; an absent store returns no rows and no store ID. Rows always require a store ID.

The recent, response and published routes read source data without submitting conversation input or starting model work, regardless of caller origin. The operator-only live route acquires the exact conversation connection; a later pane prompt submits input. Reading an absent store creates no directories and takes no writer lock. The headless host never launches the reader. Importing the panel module registers nothing, emits nothing and opens no store.

Both hosts retain text blocks in their original order, separated by one blank line. Whitespace inside each nonempty block stays exact; empty text, reasoning and tool calls are excluded. Metadata retains each source-part length and the source machine name. Response snapshots use the secondary label `Response · <working-directory base name> · <local YYYY-MM-DD HH:mm>`, from the message timestamp or, when absent, capture time. `stop` means a complete response, not accepted work; `toolUse` labels text before tool calls. Length, error, aborted, pending, deferred and unknown stops remain partial. The ordinary reader walks at most 2000 ancestors from one captured leaf and returns at most 30 responses. The native reader uses bounded public conversation pages with one captured cutoff and the same limits. Exact native reads verify visibility in that conversation. A preview is never the document; over-limit full source fails rather than becoming a truncated snapshot.

## Client-local reveal

Only an explicit local operator action lazily imports `reveal.ts`. It saves a response snapshot in this client's `markdown.dir`, or selects a stored document and its exact current revision. For a published document listed by a native host, the host names its store root and `storeId`. The adapter opens that root only when a store with that identity is readable there, and it opens the listed row's revision. If that revision's digest differs from the row's digest, the adapter refuses. A newer current revision is not an error: the reader shows its update notice. A remote or unavailable root is an error; no import or transfer is implied. The app path always comes from this client's `markdown.app`, never from a host root or document.

For a GUI action, the adapter captures terminal origin concurrently with saving through the fixed package-relative Rex helper. Its four-second timeout exceeds the helper's own child deadline plus process start, so a slow terminal still yields the helper's result. Both operations finish before the adapter writes the open request. A missing helper, failure or null result leaves the request without terminal origin. The default pane route then reports unavailable; only an explicit `window` command permits a standalone window without that origin. The [terminal-origin contract](../../docs/conventions/terminal-origin.md) owns that envelope. The helper runs in the opening process, not the producer.

After saving, the adapter writes a pinned open request. The default route invokes the fixed package-relative [terminal-pane subprocess](../../docs/conventions/terminal-pane.md) with that captured origin, its configured native executable and the literal arguments `--pane <requestPath>`. Rex owns exact origin validation and creates one split in the anchor's tab. Markdown neither interprets exact Rex fields nor selects a target. Its seven-second helper timeout exceeds Rex's five-second child deadline plus startup. The adapter retains Rex's opaque placement receipt separately from native acceptance. It never retries an uncertain dispatch, reuses an existing pane, closes an unconfirmed pane or falls back to a standalone window.

Pane intake requires `Contents/Resources/build.json` markers `{contract: 1, pane: 1, paneOpenRequest: 1}`. It never substitutes an unpinned document ID. The explicit `window` form requires contract 1 and invokes exactly `/usr/bin/open -a <client markdown.app> <requestPath>`. No document or provenance field supplies an executable. A missing or incompatible app names `node extensions/markdown/native/build.mts` as the remedy. The store removes leftover open requests older than one day within its scan bound.

Saved, pane unavailable, pane creation uncertain, accepted by the reader, acceptance not confirmed and reveal failed are distinct states. A notice says "Saved" only when the action wrote a new snapshot revision; for a document that already existed it says "Selected". After a successful launch, the adapter observes request removal for up to five seconds with an abortable wait. No removal or a failed acceptance watch means acceptance is unconfirmed; the saved document remains available. An unconfirmed pane notice forbids automatic retry. An unconfirmed explicit window notice names the build command without diagnosing the app build. Acceptance does not establish rendering, focus or human comprehension. Launch failure also preserves the document.

Editor launch requires the separate `editorOpen: 1` build marker and passes literal `--editor --surface pane|window --store <root> --intent scratchpad|file|edit|copy` arguments. New and local-file actions do not create a stored snapshot. Edit and Copy pass a pinned request for the selected source and revision; a response first retains its exact captured source. The app executable comes only from the configured local installation. An explicit separate editor window uses `/usr/bin/open -n -a <client markdown.app> --args ...`; a pane failure never selects it. Scratchpad and file dispatch notices do not claim native readiness or keyboard focus. The native app owns private recovery and automatic or explicit save outcomes, not the Pi launch adapter.

The action captures target and entry identity before asynchronous work. A changed row, scope, query, conversation or closed view aborts acquisition, also for Read latest. A selection that moves because a list arrived is not a row change. Session switch, fork, tree navigation and shutdown also withdraw every ordinary action. Each new ordinary action captures the current lifecycle signal together with its view or command signal. The adapter checks that signal after acquisition, before materialization and immediately before reveal. A snapshot saved before withdrawal remains saved, but no stale action writes an open request or launches the reader. Headless publication, background updates and replay never change window return context.
