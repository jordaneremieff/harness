# Replies and outcomes

Read this for a reply, an outcome request or report, or an explicitly sustained sequence. A single challenge that ends at delivery does not need it. The main skill governs the argument, delivery lane, and confirmation in every round.

## Get the reply

A new reply to the last challenge opens follow-up triage. Use the operator's paste when supplied, including an excerpt they edited. For a direct message, use a reply through the existing route. If the operator requests a readback, use the exact result reference when one exists. You can also read back an operator-carried message when the operator names the session and you can tie a reply to what was actually pasted. A copy alone proves no paste. Use the named-session procedure from the main skill; read only the relevant exchange. If you cannot identify the reply, ask for the excerpt rather than attribute an unrelated answer. Unrelated activity, a send receipt and elapsed time are not replies.

If no reply is visible, give any requested readback and say whether there is no reply in the available record or no access to check. Do not poll, set a timer or retry the send. An instruction to check again permits one check, not another send.

For a requested continuation, tell the operator who brings back the reply. After a clipboard handoff, that is the operator unless they ask for a named-session readback. For a direct request with a result due here, follow the host's own controls: a live ordinary session can yield the turn with `agent_yield`; a Durable agent with a routed request can retain it with `agent_work` and the exact result reference. A one-shot process that exits will not resume on its own. Without a live return route, ask the operator to bring back the reply rather than promise automatic follow-up.

## Decide what changed

- **Reasoned defense.** If the reply resolves the challenge on its own terms, stop and say what answered it. If a premise still depends on a consequential fact or inference, name that gap and what would settle it. Coherence alone is not proof; a missing fact is not a refutation. Raise a new unsupported claim only if the original challenge turns on it.
- **Verified refutation.** When evidence in the supplied record defeats a premise, correct it and drop all claims that depend on it. Do not substitute a new accusation. Stop if nothing consequential remains. A bare assertion is not verification. Do not investigate the codebase or mine the recipient's tool outputs to decide who is right.
- **Movement or action.** Credit only the specific change. Agreement and announced intent are not completed action. If the reply says a relevant check is in progress, pause for its result rather than repeat the request. If the record shows completed action or someone reports it, end the sequence with readback. Only a new operator instruction can reopen a surviving challenge, subject to the reply requirement below.
- **Decline or real boundary.** Stop if the recipient declines the challenge or names a restriction that actually bars the step. Say what moved, what remains blocked, and what authority is missing, if any. If the operator alone can answer a question, stop and relay it verbatim. The argument cannot supply permission; if the operator can lift the restriction, they do so through their own channel.

If the recipient explicitly recognises the exercise, report it. Their agreement is not evidence of unaided reconsideration. Keep independently checkable facts and do not infer unawareness from silence. Do not intensify, repackage or resend the challenge in response to recognition.

## Continue or stop

Continue only when the operator's request covers follow-up, a fresh reply leaves a specific consequential challenge unanswered, and no stop condition applies. Stop if the operator calls it. Tie the surviving gap to the operator's original concern. If settling it would no longer change that conclusion, leave it alone. Address what the recipient just said; do not restage the opening argument. Keep the same lane unless the operator changes it. Never use a different lane to bypass a decline. Use the main confirmation to say what changed.

Only an explicit sustained request permits rounds without new operator contact. Count the initial challenge and each follow-up as one round; each follow-up still requires a new reply. End a sustained sequence with an outcome readback no later than round three, even if the latest reply is not yet visible. Your confirmations and reports do not reset the count. After the readback, only a new operator instruction to continue starts a fresh bounded sequence, subject to the same reply and stop rules.

## Outcome readback

When the operator supplies or asks for an outcome, or a sustained sequence stops, give these four named rows before any judgment:

1. **What the target said.** Quote or attribute the relevant position or response.
2. **What it reportedly did.** Distinguish reported action from observed action. For a named session, cite what the relevant recent action record actually shows. Label announced intent as intent, not action.
3. **What supplied evidence establishes.** State only the result that follows from the supplied evidence. The action record belongs in the previous row, not in the argument about who was right. Agreement alone establishes no result; a useful action does not validate every premise.
4. **What remains unknown.** Include missing replies, unavailable inspection, or unverified completion where material.

Then give one recommendation: stop and name why; press again if the operator directs it and a named consequential gap remains; or have the operator supply the missing authorization through their own channel. Readback alone never authorizes another message.
